# Шаги реализации Pumping Iron

Учебный журнал: что сделано, в каком порядке и почему. Дополняется после каждого этапа.

## Шаг 1. Репозиторий и проект

- `git init -b main`, `.gitignore` (venv, кэши, `*.db`, `.env`).
- `uv init --app` создаёт пакет в `src/pumping_iron/` и `pyproject.toml`; зависимости ставятся через `uv add`, версии фиксируются в `uv.lock`.
- Запуск: `uv run pumping-iron` (функция `main()` в `__init__.py` стартует uvicorn с reload).

## Шаг 2. Каркас FastAPI

- `main.py` создаёт приложение, подключает статику и роуты страниц.
- Список разделов один раз описан в `PAGES` (путь, шаблон, название, цвет блина). Из него строятся навбар, роуты и штанга на главной.
- Шаблоны Jinja2: `base.html` (навбар, подключение стилей) и по одному файлу на раздел через `{% extends %}`.

## Шаг 3. Дизайн

- Идея: тренажёрный зал, а не типовой SaaS. Каждый раздел это блин штанги своего цвета (красный, синий, жёлтый, зелёный, белый, оранжевый); цвет повторяется в навбаре и заголовке.
- Цвета и шрифты вынесены в CSS-переменные (`:root`), цвет раздела задаётся классом `.plate-<цвет>` через `--plate` и `--on`.
- Главная: симметричная штанга, по три блина на сторону (`.side-left` использует `flex-direction: row-reverse`, поэтому в DOM блины идут по порядку навбара). Единственная анимация: блины «надеваются» на гриф, отключается при `prefers-reduced-motion`.

## Шаг 4. Блок 3: чат с ИИ-тренером

- `assistant.py`: `POST /api/chat` принимает историю сообщений, добавляет системный промпт тренера и стримит ответ из LM Studio (OpenAI-совместимый API, `stream=true`, строки SSE `data: {...}`).
- Адрес и модель берутся из `LMSTUDIO_URL` и `LMSTUDIO_MODEL`.
- `static/chat.js` читает ответ через `fetch` и `ReadableStream`, дописывая текст в пузырь; текст вставляется через `textContent`, чтобы не было XSS.
- Сервер не хранит историю: клиент присылает её целиком.
- Проверка без LM Studio: заглушка с тем же API (в scratchpad), плюс случай «сервер недоступен».

## Шаг 5. Блок 1: программа тренировок и журнал (SQLite)

- **Хранилище.** `db.py` на стандартном `sqlite3` (без ORM: проект маленький, зависимостей меньше). Таблицы: `muscle_groups`, `exercises`, `program_items`, `log_entries`; внешние ключи включены (`PRAGMA foreign_keys = ON`), ограничения `CHECK` защищают от нулевых и отрицательных значений. Схема и справочник упражнений создаются при старте (`lifespan` в `main.py`), повторный запуск ничего не дублирует.
- **Комплементарные группы и антагонисты.** В `muscle_groups` поле `movement` (push/pull/legs/core) объединяет группы, работающие вместе (грудь, плечи, трицепс), а `antagonist_id` указывает на противоположную группу (грудь и спина, бицепс и трицепс). На странице программы под днём подсказка «Без антагониста: …», если пары в этот день нет.
- **Роуты.** `workouts.py`: GET-страницы рендерят HTML, изменения идут обычными HTML-формами `POST` и отвечают редиректом 303 (post/redirect/get), поэтому обновление страницы не повторяет действие и JS не нужен. Ошибочные данные отсекает валидация `Form(ge=..., le=...)` (422), нарушение ограничений БД превращается в 400.
- **Подключение к БД.** Зависимость `get_db` даёт подключение на запрос; запись коммитится внутри эндпоинта (`with db:`), чтобы данные были сохранены до того, как браузер перейдёт по редиректу.
- **Журнал.** Одна строка на подход; после записи форма открывается с предыдущими значениями, чтобы быстро вносить следующие подходы.
- **Общий код.** `web.py` держит `PAGES`, объект шаблонов и функцию `page()`, чтобы роутеры и `main.py` не импортировали друг друга по кругу.

## Шаг 6. Блок 6: питание и дневник (SQLite)

- **Две таблицы.** `diet_items` это рацион (план на день: продукт, граммы, ккал, белки, жиры, углеводы по приёмам пищи). `food_log` это дневник: что реально съедено в конкретную дату. Рацион и дневник повторяют пару «программа и журнал» из шага 5.
- **Мониторинг.** Страница `/nutrition/log` показывает выбранный день (стрелки для перехода), итог «съедено из плана», кнопки «съел по рациону» (копируют строку плана в дневник одним запросом `INSERT ... SELECT`) и таблицу итогов за последние 14 дней. Эти итоги пригодятся для графиков в блоке 5.
- **Общий код.** Функция `write()` переехала в `db.py`, потому что ей пользуются оба роутера; `group_by_meal()` считает суммы и для рациона, и для дневника.
- **Индексы.** `idx_food_log_date` ускоряет выбор по дате и группировку для истории.

## Шаг 7. ИИ тренер меняет данные сам (tool calling)

- **Идея.** Модель получает описание инструментов (`add_to_program`, `add_to_diet`) в формате функций OpenAI, который понимает LM Studio. Когда она отвечает не текстом, а вызовом инструмента, сервер выполняет его и возвращает результат модели, после чего она продолжает ответ.
- **Контекст.** В системный промпт на каждый запрос подставляются справочник упражнений, текущая программа, рацион и сегодняшние калории. Поэтому модель использует точные названия и не дублирует уже добавленное.
- **Стриминг вызовов.** Вызов приходит кусками: имя один раз, JSON-аргументы по частям. `stream_reply` склеивает куски по индексу вызова, затем выполняет их и делает следующий раунд (не больше `MAX_TOOL_ROUNDS = 5`, чтобы цикл не зациклился).
- **Безопасность.** Все аргументы проверяются как внешний ввод (диапазоны, список приёмов пищи, существование упражнения). Ошибка возвращается модели текстом, чтобы она могла исправиться; пользователь видит строку «✅ …» только для успешных изменений. Дубликаты отклоняются, поэтому повтор запроса ничего не задваивает.
- **Нет `lower()` для кириллицы.** В SQLite `lower()` работает только с ASCII, поэтому имена сравниваются в Python через `casefold()`.
- **Проверка.** Заглушка LM Studio в scratchpad отдаёт вызовы кусками (включая ошибочный), тест проверяет записи в БД и повторный запрос.

## Шаг 8. Доработка чата по замечаниям консультантов

- **Протокол ответа.** Вместо простого текста сервер шлёт NDJSON: строка на событие `text`, `notice` или `error`. Клиент собирает историю только из `text`, поэтому плашки «✅ …» и ошибки не попадают в историю и модель не принимает их за свои слова. Чтение построчное с буфером, потому что сетевой кусок может оборваться посреди строки.
- **Разбор SSE.** `parse_sse_line()` пропускает мусор, оборванный JSON и маркер `[DONE]`, принимает `data:` без пробела. Ошибка, пришедшая внутри потока (`{"error": ...}`), показывается пользователю.
- **Лимит раундов.** Последний допустимый раунд отправляется без `tools`, и модель обязана ответить текстом. Если и тогда приходят вызовы, пользователь видит сообщение о лимите.
- **Двойная отправка.** Нажатие Enter обходит `disabled` кнопки, поэтому в `chat.js` добавлен флаг `sending`.
- **Названия.** Инструменты отклоняют названия длиннее 80 символов (как формы) и схлопывают переводы строк в пробелы, чтобы сохранённое название не выглядело как инструкция в системном промпте.
- **Баг по ходу.** Рацион сначала не попадал в контекст ИИ из-за молча не сработавшей автозамены в скрипте-патче. Урок: после правки проверять результат, а не только отсутствие ошибки.

## Шаг 9. Блок 2: замеры, фигура и фото прогресса

- **Таблицы.** `measure_types` (справочник: ключ, название, единица, допустимый диапазон, что считать улучшением `better`) и `measurements` (дата, тип, значение, `UNIQUE (дата, тип)`: повторный ввод заменяет значение через `ON CONFLICT DO UPDATE`). Справочник засевается отдельной проверкой на пустоту, поэтому в уже существующей БД он появляется сам.
- **Процент изменения.** `summarize()` сравнивает последнее значение с первым значением внутри периода, отсчитанного от даты последнего замера (а не от сегодняшней), поэтому пауза в измерениях не обнуляет страницу. Цвет задаёт `better`: рост бицепса зелёный, рост талии красный, бёдра и вес без оценки.
- **Фигура.** Нарисованный от руки силуэт заменён готовой анатомической картой мышц (вид спереди): полигоны из MIT-библиотеки react-body-highlighter лежат в `body_figure.py`, лицензия в `THIRD_PARTY_NOTICES.md`. Все полигоны рисуются нейтральным цветом, а поверх них закрашиваются области замеренных частей тела: зелёный, красный или серый по тому же `tone`, что и процент. Словарь `FIGURE` в `body.py` связывает замер с мышцами и стороной (полигон принадлежит правой стороне человека, если его центр левее середины рисунка), а точка выноски считается как среднее центров полигонов. Подписи остаются HTML-блоками в боковых колонках; линии-выноски рисуются в SVG с системой координат 100 × (100·ratio), чтобы единица была одинаковой по обеим осям. Строки подписей разнесены минимум на 13 %, на узких экранах шрифт уменьшается.
- **Ввод прямо у фигуры.** Значение в каждой подписи (и вес с жиром над фигурой) это `<input type="number">` с последним сохранённым числом; всё внутри одной формы `POST /body/measure`. `static/body.js` на событии `input` пересчитывает процент по тем же правилам, что `summarize()`: база для сравнения приходит с сервера в `data-base` (первое значение периода, а если замер один и он не сегодняшний, то он сам), цвет берётся из `data-better`, область тела на фигуре перекрашивается через `id="reg-<ключ>"`. Кнопка «Сохранить» неактивна, пока ничего не изменено, а при отправке неизменённые поля отключаются (`disabled`), поэтому на сервер уходят только правки. Дату сервер ставит сам (сегодня); повторное сохранение в тот же день заменяет значение. Старая отдельная форма «Внести замеры» удалена, чтобы ввод был в одном месте. Без JS форма тоже работает, но отправит все поля.
- **Значки.** Иконки лежат в `icons.py` как словарь кусочков SVG; функция `icon('имя')` зарегистрирована глобально в Jinja и вставляет `<svg>` без внешних файлов и запросов. Цвет и размер иконка берёт у соседнего текста (`stroke: currentColor`, `1.15em`), поэтому в кнопке, вкладке и баннере она сама окрашивается в нужный цвет. Стрелки ▲ ▼ у процентов это обычные символы текста, их добавляют `summarize()` и `body.js`.
- **Диапазоны.** Значение вне диапазона типа (например, 3.8 вместо 38 см), нечисло, `nan` и дата в будущем отклоняются кодом 422.
- **Фото.** Файлы лежат в `data/photos/` под случайными именами, в БД только метаданные. Тип определяется по первым байтам файла, а не по имени и заголовку клиента; размер ограничен 10 МБ; отдаются фото только через `/body/photos/{id}/file`, так что путь клиент не выбирает. Папка `data/` в `.gitignore`: фото личные.
- **Напоминание.** Баннер на каждой странице, когда последнему фото 14 дней и больше. Он виден только когда приложение открыто: фоновой службы нет. Системное напоминание (Планировщик задач Windows) можно добавить отдельно.
- **Демо-данные.** Для предварительного просмотра используется отдельная БД `data/demo/demo.db`, реальная база не затрагивается.
