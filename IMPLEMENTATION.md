# Шаги реализации Pumping Iron

Учебный журнал: что сделано, в каком порядке и почему. Дополняется после каждого этапа.

## Шаг 1. Репозиторий и проект

- `git init -b main`, `.gitignore` (venv, кэши, `*.db`, `.env`).
- `uv init --app` создаёт пакет в `src/pumping_iron/` и `pyproject.toml`; зависимости ставятся через `uv add`, версии фиксируются в `uv.lock`.
- Запуск: `uv run pumping-iron` (функция `main()` в `__init__.py` стартует uvicorn с reload).

## Шаг 2. Каркас FastAPI

- `main.py` создаёт приложение, подключает статику и роуты страниц.
- Список разделов один раз описан в `PAGES` (путь, шаблон, название, цвет блина, значок). Из него строятся навбар, роуты и штанга на главной.
- Шаблоны Jinja2: `base.html` (навбар, подключение стилей) и по одному файлу на раздел через `{% extends %}`.

## Шаг 3. Дизайн

- Идея: тренажёрный зал, а не типовой SaaS. Каждый раздел это блин штанги своего цвета (красный, синий, жёлтый, зелёный, белый, оранжевый); цвет повторяется в навбаре и заголовке.
- Цвета и шрифты вынесены в CSS-переменные (`:root`), цвет раздела задаётся классом `.plate-<цвет>` через `--plate` и `--on`.
- Главная: симметричная штанга, по три блина на сторону (`.side-left` использует `flex-direction: row-reverse`, поэтому в DOM блины идут по порядку навбара). Единственная анимация: блины «надеваются» на гриф, отключается при `prefers-reduced-motion`.

## Шаг 4. Блок 3: чат с ИИ-тренером

- `assistant.py`: `POST /api/chat` принимает историю сообщений, добавляет системный промпт тренера и стримит ответ из LM Studio (OpenAI-совместимый API, `stream=true`, строки SSE `data: {...}`).
- Адрес и модель берутся из `LMSTUDIO_URL` и `LMSTUDIO_MODEL`.
- `static/chat.js` читает ответ через `fetch` и `ReadableStream`, дописывая текст в пузырь; текст вставляется через `textContent`, чтобы не было XSS.
- Сервер не хранит историю: клиент присылает её целиком.
- Проверка без LM Studio: заглушка с тем же API (в scratchpad), плюс случай «сервер недоступен».

## Шаг 5. Блок 1: программа тренировок и журнал (SQLite)

- **Хранилище.** `db.py` на стандартном `sqlite3` (без ORM: проект маленький, зависимостей меньше). Таблицы: `muscle_groups`, `exercises`, `program_items`, `log_entries`; внешние ключи включены (`PRAGMA foreign_keys = ON`), ограничения `CHECK` защищают от нулевых и отрицательных значений. Схема и справочник упражнений создаются при старте (`lifespan` в `main.py`), повторный запуск ничего не дублирует.
- **Комплементарные группы и антагонисты.** В `muscle_groups` поле `movement` (push/pull/legs/core) объединяет группы, работающие вместе (грудь, плечи, трицепс), а `antagonist_id` указывает на противоположную группу (грудь и спина, бицепс и трицепс). На странице программы под днём подсказка «Без антагониста: …», если пары в этот день нет.
- **Роуты.** `workouts.py`: GET-страницы рендерят HTML, изменения идут обычными HTML-формами `POST` и отвечают редиректом 303 (post/redirect/get), поэтому обновление страницы не повторяет действие и JS не нужен. Ошибочные данные отсекает валидация `Form(ge=..., le=...)` (422), нарушение ограничений БД превращается в 400.
- **Подключение к БД.** Зависимость `get_db` даёт подключение на запрос; запись коммитится внутри эндпоинта (`with db:`), чтобы данные были сохранены до того, как браузер перейдёт по редиректу.
- **Журнал.** Одна строка на подход; после записи форма открывается с предыдущими значениями, чтобы быстро вносить следующие подходы.
- **Общий код.** `web.py` держит `PAGES`, объект шаблонов и функцию `page()`, чтобы роутеры и `main.py` не импортировали друг друга по кругу.

## Шаг 6. Блок 6: питание и дневник (SQLite)

- **Две таблицы.** `diet_items` это рацион (план на день: продукт, граммы, ккал, белки, жиры, углеводы по приёмам пищи). `food_log` это дневник: что реально съедено в конкретную дату. Рацион и дневник повторяют пару «программа и журнал» из шага 5.
- **Мониторинг.** Страница `/nutrition/log` показывает выбранный день (стрелки для перехода), итог «съедено из плана», кнопки «съел по рациону» (копируют строку плана в дневник одним запросом `INSERT ... SELECT`) и таблицу итогов за последние 14 дней. Эти итоги пригодятся для графиков в блоке 5.
- **Общий код.** Функция `write()` переехала в `db.py`, потому что ей пользуются оба роутера; `group_by_meal()` считает суммы и для рациона, и для дневника.
- **Индексы.** `idx_food_log_date` ускоряет выбор по дате и группировку для истории.

## Шаг 7. ИИ тренер меняет данные сам (tool calling)

- **Идея.** Модель получает описание инструментов (`add_to_program`, `add_to_diet`) в формате функций OpenAI, который понимает LM Studio. Когда она отвечает не текстом, а вызовом инструмента, сервер выполняет его и возвращает результат модели, после чего она продолжает ответ.
- **Контекст.** В системный промпт на каждый запрос подставляются справочник упражнений, текущая программа, рацион и сегодняшние калории. Поэтому модель использует точные названия и не дублирует уже добавленное.
- **Стриминг вызовов.** Вызов приходит кусками: имя один раз, JSON-аргументы по частям. `stream_reply` склеивает куски по индексу вызова, затем выполняет их и делает следующий раунд (не больше `MAX_TOOL_ROUNDS = 5`, чтобы цикл не зациклился).
- **Безопасность.** Все аргументы проверяются как внешний ввод (диапазоны, список приёмов пищи, существование упражнения). Ошибка возвращается модели текстом, чтобы она могла исправиться; пользователь видит строку «✅ …» только для успешных изменений. Дубликаты отклоняются, поэтому повтор запроса ничего не задваивает.
- **Нет `lower()` для кириллицы.** В SQLite `lower()` работает только с ASCII, поэтому имена сравниваются в Python через `casefold()`.
- **Проверка.** Заглушка LM Studio в scratchpad отдаёт вызовы кусками (включая ошибочный), тест проверяет записи в БД и повторный запрос.

## Шаг 8. Доработка чата по замечаниям консультантов

- **Протокол ответа.** Вместо простого текста сервер шлёт NDJSON: строка на событие `text`, `notice` или `error`. Клиент собирает историю только из `text`, поэтому плашки «✅ …» и ошибки не попадают в историю и модель не принимает их за свои слова. Чтение построчное с буфером, потому что сетевой кусок может оборваться посреди строки.
- **Разбор SSE.** `parse_sse_line()` пропускает мусор, оборванный JSON и маркер `[DONE]`, принимает `data:` без пробела. Ошибка, пришедшая внутри потока (`{"error": ...}`), показывается пользователю.
- **Лимит раундов.** Последний допустимый раунд отправляется без `tools`, и модель обязана ответить текстом. Если и тогда приходят вызовы, пользователь видит сообщение о лимите.
- **Двойная отправка.** Нажатие Enter обходит `disabled` кнопки, поэтому в `chat.js` добавлен флаг `sending`.
- **Названия.** Инструменты отклоняют названия длиннее 80 символов (как формы) и схлопывают переводы строк в пробелы, чтобы сохранённое название не выглядело как инструкция в системном промпте.
- **Баг по ходу.** Рацион сначала не попадал в контекст ИИ из-за молча не сработавшей автозамены в скрипте-патче. Урок: после правки проверять результат, а не только отсутствие ошибки.

## Шаг 9. Блок 2: замеры, фигура и фото прогресса

- **Таблицы.** `measure_types` (справочник: ключ, название, единица, допустимый диапазон, что считать улучшением `better`) и `measurements` (дата, тип, значение, `UNIQUE (дата, тип)`: повторный ввод заменяет значение через `ON CONFLICT DO UPDATE`). Справочник засевается отдельной проверкой на пустоту, поэтому в уже существующей БД он появляется сам.
- **Процент изменения.** `summarize()` сравнивает последнее значение с первым значением внутри периода, отсчитанного от даты последнего замера (а не от сегодняшней), поэтому пауза в измерениях не обнуляет страницу. Цвет задаёт `better`: рост бицепса зелёный, рост талии красный, бёдра и вес без оценки.
- **Фигура.** Нарисованный от руки силуэт заменён готовой анатомической картой мышц (вид спереди): полигоны из MIT-библиотеки react-body-highlighter лежат в `body_figure.py`, лицензия в `THIRD_PARTY_NOTICES.md`. Все полигоны рисуются нейтральным цветом, а поверх них закрашиваются области замеренных частей тела: зелёный, красный или серый по тому же `tone`, что и процент. Словарь `FIGURE` в `body.py` связывает замер с мышцами и стороной (полигон принадлежит правой стороне человека, если его центр левее середины рисунка), а точка выноски считается как среднее центров полигонов. Подписи остаются HTML-блоками в боковых колонках; линии-выноски рисуются в SVG с системой координат 100 × (100·ratio), чтобы единица была одинаковой по обеим осям. Строки подписей разнесены минимум на 13 %, на узких экранах шрифт уменьшается.
- **Ввод прямо у фигуры.** Значение в каждой подписи (и вес с жиром над фигурой) это `<input type="number">` с последним сохранённым числом; всё внутри одной формы `POST /body/measure`. `static/body.js` на событии `input` пересчитывает процент по тем же правилам, что `summarize()`: база для сравнения приходит с сервера в `data-base` (первое значение периода, а если замер один и он не сегодняшний, то он сам), цвет берётся из `data-better`, область тела на фигуре перекрашивается через `id="reg-<ключ>"`. Кнопка «Сохранить» неактивна, пока ничего не изменено, а при отправке неизменённые поля отключаются (`disabled`), поэтому на сервер уходят только правки. Дату сервер ставит сам (сегодня); повторное сохранение в тот же день заменяет значение. Старая отдельная форма «Внести замеры» удалена, чтобы ввод был в одном месте. Без JS форма тоже работает, но отправит все поля.
- **Значки.** Иконки лежат в `icons.py` как словарь кусочков SVG; функция `icon('имя')` зарегистрирована глобально в Jinja и вставляет `<svg>` без внешних файлов и запросов. Цвет и размер иконка берёт у соседнего текста (`stroke: currentColor`, `1.15em`), поэтому в кнопке, вкладке и баннере она сама окрашивается в нужный цвет. Стрелки ▲ ▼ у процентов это обычные символы текста, их добавляют `summarize()` и `body.js`.
- **Диапазоны.** Значение вне диапазона типа (например, 3.8 вместо 38 см), нечисло, `nan` и дата в будущем отклоняются кодом 422.
- **Фото.** Файлы лежат в `data/photos/` под случайными именами, в БД только метаданные. Тип определяется по первым байтам файла, а не по имени и заголовку клиента; размер ограничен 10 МБ; отдаются фото только через `/body/photos/{id}/file`, так что путь клиент не выбирает. Папка `data/` в `.gitignore`: фото личные.
- **Напоминание.** Баннер на каждой странице, когда последнему фото 14 дней и больше. Он виден только когда приложение открыто: фоновой службы нет. Системное напоминание (Планировщик задач Windows) можно добавить отдельно.
- **Демо-данные.** Для предварительного просмотра используется отдельная БД `data/demo/demo.db`, реальная база не затрагивается.

## Шаг 10. Цитата дня на главной

- **365 цитат на день года.** Они лежат в `quotes.txt` (строка `вид|автор|источник|русский|английский|кто перевёл`), а не в коде: файл можно править руками, не трогая Python. `quotes.py` читает его при старте, перемешивает каждый вид с фиксированным зерном и равномерно перемежает виды (`s` мысль, `d` заряд). `quote_of_the_day()` берёт номер дня в году, поэтому цитата не меняется при перезагрузке страницы и одна и та же в течение суток. 366-й день високосного года повторяет первую цитату.
- **Откуда тексты.** 241 цитата взята из текстов в общественном достоянии (Gutenberg, Wikisource): Марк Аврелий (пер. Касобона), Эпиктет (Кроссли), Сенека (Гуммере), Франклин «Путь к богатству», Дхаммапада (Мюллер), Лао-цзы (Легге), Ксенофонт (Дакинс). Английский текст дословно из этих изданий. Русский текст взят из опубликованных литературных переводов там, где их удалось найти в сети (56 цитат: Марк Аврелий в переводе С. Роговина, Дхаммапада В. Топорова, часть Эпиктета в переводе В. Алексеева; переводчик указан в подписи), у остальных перевод мой; у немецких и латинских цитат (Ницше, Ювенал, Сенека-трагик, Вергилий) показан английский перевод Claude, самого языка оригинала нет. Номера книг «Размышлений» не указаны: разбор источника путал нумерацию. Современные высказывания (Али, Рон, Эдисон и др.) записаны по памяти и помечены «источник не проверен». 124 афоризма написал я сам по-русски, у них автор «Claude» и английская версия моего перевода.
- **Два блока.** У каждой цитаты две версии: слева английская, справа русская (у моих афоризмов подпись автора стоит под русской). На узком экране блоки встают друг под другом. Слова появляются по очереди (`--w` задерживает каждое на 40 мс), при `prefers-reduced-motion` анимации нет.
- **Другая цитата.** Кнопка под цитатой это обычная ссылка `/?shift=N#quote`. При каждой отрисовке сервер выбирает случайное `N` (не равное текущему), поэтому каждое нажатие даёт новую случайную цитату, скрипт не нужен. `shift` сдвигает выбор от сегодняшней цитаты по кругу; без параметра показывается цитата дня.
- **Проверка.** Заглушка LM Studio в scratchpad отдаёт вызовы кусками (включая ошибочный), тест проверяет записи в БД и повторный запрос.

## Шаг 8. Доработка чата по замечаниям консультантов

- **Протокол ответа.** Вместо простого текста сервер шлёт NDJSON: строка на событие `text`, `notice` или `error`. Клиент собирает историю только из `text`, поэтому плашки «✅ …» и ошибки не попадают в историю и модель не принимает их за свои слова. Чтение построчное с буфером, потому что сетевой кусок может оборваться посреди строки.
- **Разбор SSE.** `parse_sse_line()` пропускает мусор, оборванный JSON и маркер `[DONE]`, принимает `data:` без пробела. Ошибка, пришедшая внутри потока (`{"error": ...}`), показывается пользователю.
- **Лимит раундов.** Последний допустимый раунд отправляется без `tools`, и модель обязана ответить текстом. Если и тогда приходят вызовы, пользователь видит сообщение о лимите.
- **Двойная отправка.** Нажатие Enter обходит `disabled` кнопки, поэтому в `chat.js` добавлен флаг `sending`.
- **Названия.** Инструменты отклоняют названия длиннее 80 символов (как формы) и схлопывают переводы строк в пробелы, чтобы сохранённое название не выглядело как инструкция в системном промпте.
- **Баг по ходу.** Рацион сначала не попадал в контекст ИИ из-за молча не сработавшей автозамены в скрипте-патче. Урок: после правки проверять результат, а не только отсутствие ошибки.

## Шаг 9. Блок 2: замеры, фигура и фото прогресса

## Шаг 11. ИИ тренер на практике: локальная модель или Claude API

- **Проверка на живой модели.** Раньше тренер работал только с заглушкой. Первый реальный прогон на LM Studio (RTX 4060, 8 ГБ): `google/gemma-4-26b-a4b` (18 ГБ, не влезает в видеопамять, считается в основном на процессоре) вызвала инструменты верно, но ответ занимал 85-300 с; `qwen/qwen3.5-9b` (6,5 ГБ) быстрее (вопрос 28 с, программа 88 с), но после вызова инструментов иногда не пишет итоговый текст, а в ответ просачиваются рассуждения, и вес упражнения она выдумывает (25 кг), если его не назвали. Вывод: для живого чата нужна модель, целиком помещающаяся в видеопамять, либо Claude.
- **Думание qwen.** Модель сначала долго «думает» (поток `reasoning_content`, сервер его не читает: LM Studio отделяет рассуждения от `content`), на это уходило 40-150 с из запроса. Параметр `chat_template_kwargs` LM Studio игнорирует, `/no_think` не помогает; помогло отключение думания в настройках модели самой LM Studio. После этого те же три теста: программа 41 с, рацион 26 с, вопрос 14 с (было 88, 165 и 28 с), итоговый текст на месте, вес не выдуман (0 кг и просьба задать). Мелкий огрех остался: на «два упражнения» модель сделала один вызов, а в тексте заявила, что взяла похожее упражнение, которого в программе нет. Поэтому по плашкам «✅» видно настоящий результат, а по тексту модели нет.
- **Системный промпт.** Добавлено: вес передавать, только если его назвал пользователь, иначе 0 и сказать об этом; после вызовов инструментов всегда писать короткий итог.
- **Переключатель на странице.** Над чатом выбор «Локальная (LM Studio)» или «Claude API (модель)». Выбор уходит в запросе (`provider`: `local` или `claude`) и запоминается в `localStorage`. Если ключа нет, вариант Claude недоступен и рядом подсказка. Страница `/assistant` теперь отдаётся роутером (`assistant.py`), а не общей таблицей `PAGES`, потому что ей нужно знать, есть ли ключ.
- **Два бэкенда в одном контракте.** `_stream_local` (httpx к LM Studio, как раньше) и `_stream_claude` (официальный SDK `anthropic`, `client.messages.stream`) отдают одни и те же NDJSON-события `text`, `notice`, `error`, поэтому `chat.js` не различает модели. Инструменты описаны один раз в формате OpenAI (`TOOLS`) и для Claude переводятся в `input_schema` (`CLAUDE_TOOLS`).
- **Цикл с инструментами у Claude.** После раунда собирается итоговое сообщение, берутся блоки `tool_use`, сервер выполняет их тем же `run_tool`, а в следующий раунд уходит всё сообщение ассистента целиком (блоки рассуждений API требует вернуть обратно) и ответы `tool_result`. Последний раунд идёт без инструментов. Отказ (`stop_reason: refusal`), неверный ключ, лимит запросов и сетевые ошибки превращаются в одно событие `error`.
- **Настройка.** Ключ берётся из `ANTHROPIC_API_KEY` (или `ANTHROPIC_AUTH_TOKEN`), модель из `ANTHROPIC_MODEL` (по умолчанию `claude-opus-5-5`, у Sonnet и Haiku запросы дешевле). Без перезапуска сервера новый ключ не подхватится.
- **Проверка без ключа.** Заглушка Anthropic API в scratchpad отдаёт SSE-события: текст, вызов инструмента кусками, отказ, 401. Проверены: полный цикл с записью в БД, отказ, неверный ключ, отсутствие ключа (страница и API), переключатель в браузере.
- **Не сделано.** Серверный запасной вариант при отказе (`fallbacks`) не включён: для тренажёрного чата отказы маловероятны, а параметр усложняет запрос. Реальный вызов Anthropic API не проверялся, ключа нет.

## Шаг 12. Блок 5: статистика

- **Модули.** `stats.py` (запросы и роутер `GET /stats`), `charts.py` (графики), `templates/stats.html`. Ничего не пишет в БД, новых таблиц нет: страница считается из журнала, дневника питания и замеров. Период тот же, что на странице показателей (30 / 90 дней, год, всё время), отсчёт от сегодняшнего дня; для веса и жира, как в `/body`, от последнего замера, чтобы пауза в измерениях не опустошала график.
- **Графики это inline SVG, собранный на сервере.** Без JS, без библиотеки и без внешних запросов, как иконки. `bar_chart` рисует столбцы (пунктирная линия `reference` для плана калорий), `line_chart` рисует линию по реальным датам, поэтому пропуск в замерах виден как пропуск. Цвет берётся из `--plate` раздела.
- **Подписи при наведении.** Каждый столбец и точка лежит в группе `.hit` (с `tabindex`, поэтому работает и с клавиатуры); при наведении в свободной полосе над графиком появляется текст вида «02.10.2026: 112 кг» и пунктирная линия к отметке, а сама отметка подсвечивается. Это чистый CSS без JS. Встроенный `<title>` не использован: он появляется с задержкой и дублировал бы подпись; у группы вместо него `aria-label` с тем же текстом. Текст стоит именно в верхней полосе, где нет столбцов, потому что в SVG порядок отрисовки равен порядку в разметке, и подпись внутри графика закрывали бы следующие столбцы. Для недель текст «неделя с 21.09.2026», для питания полная дата.
- **Баг по ходу (2).** Верхняя подпись оси у тоннажа показывала «2628.5» вместо «12628.5»: длинное число обрезалось левым краем рисунка. Для чисел от 1000 теперь без десятичных.
- **Что на странице.** Плитки (тренировок, подходов, тоннаж = повторения × вес, тренировок в неделю, серия недель подряд). Нагрузка по неделям (число тренировок и тоннаж; пустые недели остаются пустыми столбцами). Подходы по группам мышц, включая нулевые, плюс подсказка о перекосе между антагонистами (грудь и спина и т. д.), если у одной стороны не меньше 6 подходов и вдвое больше, чем у другой. Прогресс в выбранном упражнении: оценка разового максимума по формуле Эпли `вес × (1 + повторения / 30)`; для упражнения без отягощения (подтягивания) лучший подход по повторениям. Личные рекорды (за всё время). Калории по дням против рациона (не больше 60 последних дней) и средние БЖУ. Вес и жир с процентом изменения (функция `summarize` из `body.py`).
- **Рекорды одним запросом.** `MAX(weight_kg * 100000 + reps)` выбирает самый тяжёлый подход, а при равном весе тот, где больше повторений; остальные столбцы SQLite берёт из этой же строки.
- **Баг по ходу.** Столбцы сначала вышли низкими и «парящими»: у моего класса `.bar` то же имя, что у грифа штанги на главной (`.bar { height: ... }`). Переименован в `.col`. Урок: имена CSS-классов в общем файле стилей должны быть уникальны, проверять поиском по файлу.
- **Проверка.** Страница отвечает 200 на всех периодах и на пустой базе (вместо графиков подсказки со ссылкой, где внести данные), неверный период даёт 422, неизвестное упражнение показывает самое частое. Подсказка о перекосе проверена на искусственно перекошенном журнале. На 375 px горизонтальной прокрутки нет. Данные для просмотра: копия демо-БД с добавленным журналом на 12 недель и дневником на 20 дней (скрипт в scratchpad, сама `demo.db` не менялась).

## Шаг 13. ИИ тренер видит журнал, замеры и фото

- **Контекст.** Раньше модель знала только справочник упражнений, программу и рацион. Теперь `build_context` (`trainer_tools.py`) начинается с «Сегодня пт 23.10.2026», а после программы добавляет журнал (последние 5 дней тренировок: «вес×повторения» или «N повт.»), личные рекорды (`personal_records` из `stats.py`) и замеры тела с датой и изменением за 90 дней. Весь контекст около 3,5 тысяч символов, ответ на вопрос о рекордах занял 28 с (раньше такой вопрос был невозможен), цифры совпали с журналом: жим лёжа 72,5×8, приседания 107,5×7.
- **Фото к сообщению.** Под чатом раскрывающийся блок «Приложить фото прогресса»: миниатюры последних 12 фото с галочками, не больше `MAX_PHOTOS` = 2 (остальные галочки блокируются). Запрос получает `photo_ids`; сервер читает файлы через `load_photos` (`photos.py`), по id, а не по пути, поэтому клиент не выбирает файл на диске. Неизвестный id даёт 404, больше двух фото или фото у сообщения не от пользователя 422. Изображение уходит последним сообщением в формате `image_url` с `data:` URI для LM Studio и в виде блока `image` с `base64` для Claude (`with_photos`, `local_image_part`, `claude_image_part`), перед фото в текст добавляется «Приложены фото прогресса: 1) дата, поза».
- **Фото живут одно сообщение.** Сервер не хранит историю, клиент присылает только текст, поэтому фото относятся лишь к сообщению, с которым отправлены; после отправки галочки снимаются, а в пузыре пользователя видна строка «Фото: дата, поза». Хочешь спросить про те же фото ещё раз, приложи их снова.
- **Промпт.** Для фото добавлены правила: описывать только то, что видно, не оценивать процент жира и вес по фото, не ставить диагнозов. Ограничение это просьба к модели, а не гарантия.
- **Проверка.** qwen3.5-9b в LM Studio принимает изображения: на искусственной картинке (красный квадрат на белом) ответила «красный квадрат» за 4 с. Через страницу (Playwright): две галочки блокируют третью, после отправки сняты, в пузыре подпись. Минус: на пустых демо-фото (90×120) модель всё равно написала про «правильную осанку», то есть на плохом изображении она выдумывает; на настоящих фото качество не проверялось. Claude на реальном API по-прежнему не проверен (нет кредитов).
- **Чат переживает уход со страницы.** Страницы приложения обычные (каждый переход загружает страницу заново), поэтому раньше история жила только в памяти вкладки и пропадала при возврате. Теперь `chat.js` держит в `sessionStorage` историю и то, что нарисовано на экране (`view`: сообщения, куски ответа, плашки), и перерисовывает чат при загрузке; хранилище привязано к вкладке и очищается при её закрытии. Если ушёл посреди ответа, браузер обрывает запрос: событие `pagehide` сохраняет частичный ответ с пометкой `pending`, а при возврате под ним появляется «Ответ прервался…», вопрос из истории убирается, чтобы повтор не дублировал его. Сервер при обрыве прекращает генерацию, дописать ответ в фоне он не может (это потребовало бы хранить ответы на сервере).
- **Не сделано.** Фото уходят как есть (до 10 МБ каждое), без уменьшения: перед отправкой стоило бы сжимать до около 1024 px (Pillow), это ускорит запрос и снизит расход токенов у Claude.

## Шаг 14. Оформление: заголовки, значки, светлая тема

- **Заголовки.** Крупный `h1` повторял подпись в навбаре, поэтому на всех страницах кроме главной он оставлен только для скринридеров (класс `.sr-only`). Цветная плашка перед ним ушла вместе с ним.
- **Значки в навбаре.** Пятое поле в `PAGES` задаёт имя значка из `icons.py`; значок окрашен в цвет раздела и заменил цветной кружок. Шрифт ссылок 1,15 rem, значки 1,5 rem.
- **Светлая и тёмная тема.** Все цвета уже были переменными, поэтому светлая тема это второй набор значений в `:root[data-theme="light"]` (фон, текст, приглушённый цвет, белый блин, хорошо/плохо), а `color-scheme` переключает и родные элементы (поля даты, полосы прокрутки). Тексты на блинах больше не берутся из тёмной или светлой переменной темы: для них отдельные `--ink` и `--paper`, одинаковые в обеих темах. Кнопка с полукругом справа в навбаре; `theme.js` подключён в `<head>` без `defer`, чтобы тема выставилась до первой отрисовки и страница не мигала тёмным. Выбор хранится в `localStorage`, пока его нет, берётся системная настройка (`prefers-color-scheme`). Без JS остаётся тёмная тема.

## Шаг 15. Недельный рацион

- **Данные.** В `diet_items` добавлен столбец `weekday` (0 = понедельник, как в `program_items`). Старая БД мигрирует при запуске (`migrate_diet_weekday` в `db.py`): прежний рацион считался одинаковым для всех дней, поэтому его строки получают понедельник и копируются на остальные шесть дней, так что рацион после обновления значит то же самое. Повторный запуск ничего не меняет (проверено на копии демо-БД: 4 строки стали 28, два запуска подряд дали тот же результат).
- **Страница.** `/nutrition` показывает семь дней, как страница тренировок: день слева с итогом ккал и БЖУ, справа приёмы пищи этого дня и одна форма «Добавить продукт» с выбором приёма. Сверху среднее за день по дням, где рацион не пуст. После добавления и удаления браузер возвращается к нужному дню (`#day-N`).
- **Дневник.** Итог «по рациону» берётся для дня недели выбранной даты. Строки «Съел по рациону» с кнопками копирования из рациона убраны по просьбе, вместе с маршрутом `/nutrition/log/from-plan/{id}`.
- **Статистика.** Пунктир на графике калорий теперь средний день рациона (дни с пустым рационом не считаются), в подписи так и сказано.
- **ИИ тренер.** Инструмент `add_to_diet` получил обязательный `weekday`: 1-7 для дня, 0 для каждого дня недели (дни, где такой продукт уже есть в этом приёме, пропускаются; ошибка только если не осталось ни одного дня). В контекст рацион уходит по дням.
- **Не сделано.** Нет кнопки «скопировать день на другие дни» на странице: для быстрого заполнения недели пока работает просьба к тренеру («на каждый день»).

## Шаг 16. Логотип в навбаре и программа на три дня

- **Картинки.** Из постера пользователя вырезаны надпись «Pumping Iron» (`static/img/logo-title.png`) и гантель (`logo-dumbbell.png`): чёрные фигуры на прозрачном фоне, получены один раз скриптом на Pillow и numpy (в зависимости проекта они не добавлены).
- **Тема.** Файлы подключены как `mask-image`, а цвет задаёт `background-color: var(--chalk)`, поэтому логотип светлый на тёмной теме и тёмный на светлой, без отдельных картинок.
- **Расположение.** В навбаре слева надпись вместо текстового бренда, сразу правее гантель, дальше разделы; переключатель темы прижат вправо. Значки перед названиями разделов позже убраны по просьбе (остались только в `icons.py` и в `PAGES`). Оба элемента декоративные (`aria-hidden`), у ссылки на главную есть `aria-label`.
- **Программа на три дня.** Вкладка «Программа» больше не привязана к дням недели: «День 1», «День 2», «День 3» (`PROGRAM_DAYS` в `workouts.py`, столбец `program_items.day` 0-2 вместо `weekday`). Старая БД мигрирует при запуске (`migrate_program_days` в `db.py`, таблица пересоздаётся, потому что меняется CHECK): пн, вт, ср становятся днями 1-3, упражнения остальных дней недели сливаются в день 3, ничего не теряется (демо-БД: 3 + 2 + 10 упражнений, два запуска подряд дают тот же результат). Инструмент тренера `add_to_program` получил параметр `day` 1-3 вместо `weekday`. Рацион остаётся по дням недели.
- **Справочник упражнений.** Новая вкладка «Справочник» в разделе «Тренировки» (`/workouts/exercises`, шаблон `exercises.html`): упражнения по группам мышц со счётчиками и форма «Новое упражнение», перенесённая со страницы программы. Список в `SEED_EXERCISES` расширен с 21 до 121 упражнения; `seed_exercises` при каждом запуске добавляет недостающие (`INSERT OR IGNORE` по уникальному имени), так что готовые БД получают новые упражнения, а существующие и пользовательские названия не меняются. Группы выложены в три колонки (`columns: 3 16rem`, сверху вниз, чтобы короткие группы не оставляли дыр), у всего раздела «Тренировки» (программа, журнал, справочник) теперь одна широкая колонка 80 rem, как у «Показателей» (`main.plate-red`), поэтому при переключении вкладок ничего не сдвигается. Группы мышц сложены в три блока (`LIBRARY_BLOCKS` в `workouts.py`): «Верхняя часть туловища» (грудь, плечи, трицепс, спина, бицепс), «Средняя часть» (пресс, низ спины) и «Ноги» (квадрицепс, бицепс бедра, ягодицы, икры); у каждого блока заголовок с красной линией и свои три колонки. У каждого упражнения вторая строка светло-серым в скобках: короткое описание («верх груди», «ширина спины»). Оно хранится в новом столбце `exercises.description` (миграция `migrate_exercise_description`, значения лежат в `SEED_EXERCISES`); `seed_exercises` заполняет только пустые описания, поэтому свои правки и упражнения без описания (созданные формой) не затираются. Весь справочник уходит в контекст АИ тренера, поэтому он стал длиннее примерно на 3 тыс. символов.

- **Только светлая тема.** Тёмная тема и переключатель убраны по просьбе: значения светлой темы стали основными в `:root`, `theme.js`, кнопка в навбаре и значок `contrast` удалены. На главной все шесть блинов одного цвета (стальной, как у «Статистики»), углы блинов скруглены сильнее (1.1 rem вместо 0.5 rem). Цвета разделов остаются у подчёркивания, кнопок и графиков внутри страниц.

- **Фото на главной.** Штанга и блины с главной убраны вместе с заголовком «Что на штанге сегодня?» и подписью (заголовок остался скрытым для скринридеров). Вместо них широкая полоса из присланной чёрно-белой фотографии (`static/img/hero-bicep.webp`, `<img class="hero-photo">`): `object-fit: cover`, высота 24 rem, скруглённые углы 1.5 rem, `mix-blend-mode: multiply` превращает белый фон снимка в цвет страницы. Фото плавно проявляется за 1.4 с (`photo-in`), цитата начинает появляться на 0.8 с, пока фото ещё проявляется; при `prefers-reduced-motion` анимации нет.

- **Спиннер в чате.** Пока ответ не начался, в пузыре тренера вместо «…» вращающееся кольцо (`.spinner`, `addSpinner` в `chat.js`); оно убирается с первым куском ответа.
- **Кнопка «Другая цитата»** появляется последней: её задержка считается от самой длинной из двух цитат (`--n-max` на блоке), пока кнопка не показана, она невидима и не нажимается (`visibility`).
- **Зависший чат.** Разбор случая, когда ответ оборвался и форма осталась заблокированной: LM Studio в логе увидел «Client disconnected» после ~3 минут генерации (6 токенов в секунду), то есть соединение закрыл браузер. `pagehide` ставит `leaving`, и прерванный запрос молча завершался. Если страница при этом оставалась живой (восстановление из кэша «назад/вперёд»), форма больше не оживала. Теперь `pageshow` с `persisted` перезагружает страницу: сохранённый чат рисуется заново с пометкой «Ответ прервался», форма работает. Точная причина закрытия соединения в этом случае не установлена.
